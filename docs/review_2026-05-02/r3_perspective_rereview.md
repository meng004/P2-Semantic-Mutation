## 3. Residual / new perspective concerns

### 3.1 Title scope: hedge or fix?

**Verdict: cosmetic hedge with structural escape hatch.**

The title is a clean, verifiable scope tightening — *Same-Prompt* and *Single-Output Scientific Computing Kernels* are both surgical and follow R3 W2-FIX (a) verbatim. Credit where due. **But** §1.1 line 38 contains an explicit permission-slip clause: *"the narrative use of 'scientific computing programs' in the main text applies to P-series overall discussion contexts (e.g., §1.3 / §1.6) without conflict."* This authorizes the body to keep claiming the broad domain wherever the author finds it convenient. The §6.5 stakeholder section uses this permission generously:

- **Line 1346** (§6.5.1): *"Testers of **scientific computing software** have long faced the judgment dilemma…"* — no single-output qualifier.
- **Line 1359** (§6.5.2): *"MR designers (often researchers or senior developers in **scientific computing domains**)…"* — no single-output qualifier.
- **Line 1382** (§6.5.3): *"Certification bodies in high-risk domains such as nuclear engineering, aerospace, medical devices… need to examine test adequacy evidence for **scientific computing software**."* — no single-output qualifier.
- **Line 740** (§4.2.5): *"…the first work to factor-decompose 'LLM source diversity vs MR design' in the **scientific computing software domain**."* — first-of-kind claim still made at the broad-domain level.
- **Line 1492** (§7.2.1 R5): *"12 PUTs do not represent the full domain of **scientific computing software** (e.g., lacking molecular dynamics, quantum chemistry, CFD large-scale code)."* — at least this one is in the limitations section where it belongs.

Of 28 occurrences of "scientific computing" in the body, only 2 (lines 35, 38) carry the "single-output kernels" qualifier. The other 26 use the broad phrase. This pattern is not accidental — it is licensed by §1.1 line 38. From an auditor-credibility perspective, this is the *style* of fix that lawyers call a "headline + footnote": the cover protects you from a claim of overreach in the abstract-judging stage of search results / citations, while the body retains all the marketing latitude.

**Recommendation for next round**: delete the §1.1 line 38 permission clause; replace every body-text occurrence of unqualified "scientific computing" with "single-output scientific computing kernels" or, where that's awkward, with "the scientific computing kernels studied in this paper" — *especially* in the §6.5 stakeholder pain-point sentences.

The differences are limited to two short P0/P1 cross-reference markers added elsewhere (R11 chained-conditioning in §7.1.8; R13 in §7.1.9) — neither of which changes a single word in §6.5.3 itself. Specifically:

- **The numeric thresholds remain.** Lines 1387-1388: *"aligned-cell SMS ≥ 0.20 (P50) = basically adequate / aligned-cell SMS ≥ 0.30 (~P70) = adequate; C1_share ≤ 0.20 = diagnostically clear"*. The Editorial Decision arbitrated these be *deleted* (Disagreement-3 fix (b)). They remain.
- **No actual normative-text citation was added.** §8 References has no IEC 60880, ISO 26262, ASME V&V family, IEC 62304, 21 CFR 820, NIST SP 800-53, IEC 62443-4-1 entries. §6.5.3 line 1382 mentions IEC 60880 and ISO 26262 ASIL D *as obstacles* ("Current IEC/ISO standards … have no quantitative acceptance criteria for mutation testing") — but this is the same (correct) descriptive sentence the round-1 draft already had. ### 3.3 Cross-disciplinary transferability: §6.5 pragmatic or aspirational?

**Verdict: aspirational, with the §6.5.2 PR-CI fragment now functionally misleading.**

Across the four §6.5 subsections:

- **§6.5.1 (Test engineers)** — partially defensible at the *academic / national-lab maintenance phase*; indefensible at the *industrial-internal-vendor phase* because of unaddressed air-gap incompatibility (W4) and 9-step manual reproduction sequence (W3). *Same as round 1.*
- **§6.5.2 (MR designers)** — newly *worse* than round 1 in one specific way: the YAML example at lines 1364-1376 now visibly includes the W3 env-var trap (line 1373: `SMS_VERSION=v4 P2_PRIMARY_VERSION=v3b`) and presents it as a recommended template for PR-CI integration. A reader copy-pasting this fragment into their own GitHub Actions repository will land in exactly the failure mode R3 W3 described: silent-divergent reproduction. From an industrial-CI-integration standpoint, embedding the trap in a how-to YAML is the worst possible exposure — it converts an artifact-layer bug (REPRODUCIBILITY.md fragility) into a stakeholder-facing recommended pattern.
- **§6.5.3 (Auditors)** — no progress. Still aspirational. See §3.2 above.
- **§6.5.4 (Common interface)** — defensible *in principle* (single SSOT JSON), but undermined by the unfixed W3. The narrative at line 1396 ("All three stakeholder classes obtain consistent numbers through the same `data/results/paper_numbers_v4.json` (SSOT)") is true *only if* the env-var trap is set correctly; it does not say so. A reader running default tooling will get inconsistent numbers and not know it. *Same as round 1.*

The R0/R1/R2 stat-method revisions (R11/R13 chained-conditioning, downgraded H4 verdict, etc.) had nothing to do with §6.5. The author's commit pattern reveals a clear prioritization: statistical / methodological honesty was upgraded; industrial-deployability honesty was not. From a cross-disciplinary practitioner perspective, this priority is exactly inverted from where the audience-credibility risk lives — IST has many V&V-engineering readers who will mentally categorize §6.5 as "another over-claimed deployment story" and discount the rest of the paper accordingly.

### 3.4 Devil's-advocate residual on stakeholder blind spots

The Devil's Advocate (R4) round-1 report flagged "stakeholder blind spots" — specifically that §6.5 lacked an LLM-provider stakeholder (Anthropic / OpenAI / DeepSeek as supply-chain dependency). The current §6.5 has no new subsection for LLM-provider stakeholders; the dependency is acknowledged only indirectly through R10 (LLM non-determinism) at lines 1456-1463 and R11/R13 (chained conditioning + protocol asymmetry) at lines 1465-1486. None of these characterizes the *supply-chain* exposure: model deprecation, weight changes, vendor billing, terms-of-service constraints on V&V workflows.

**More importantly**, the R3-original W4 air-gap concern is itself a stakeholder-blind-spot finding (the *operational-site security-officer* stakeholder is missing). That blind spot is unfixed. The author's revision style on stakeholder analysis appears to be: *add risk-register entries (R11, R13) when reviewers escalate*, but *do not refactor §6.5 itself* to reflect those risks for stakeholders. The result is a §6.5 that promises capability and a §7 that lists impossibility — and no stakeholder-facing reconciliation between them. From a cross-disciplinary standpoint this is a credibility-eroding pattern; from a Devil's-Advocate standpoint it satisfies "added a caveat but did not close the blind spot."

### 3.5 New concern: §6.5.2 YAML fragment is now an audit-stage liability

I want to flag one issue that R3 round-1 only implicitly raised, but which the round-2 manuscript has *worsened*. The §6.5.2 GitHub Actions YAML at lines 1364-1376 is functionally mis-leading in three independent ways:

1. **Env-var trap**: line 1373 hardcodes both `SMS_VERSION=v4` and `P2_PRIMARY_VERSION=v3b`. A reader who adapts this YAML to their own PUT/MR will inherit both the v4 cross-source defaults and the v3b post-hoc c-class primary MP selection. The latter is an *exploratory analysis condition*, not a baseline configuration. Embedding it in a CI template effectively asks every adopter to inherit the §3.5.1 selection-on-the-response confound the rest of the paper just spent §3.5.1 + §7.1.8 R11 disclosing. This is structurally worse than W3 round-1 — it propagates the post-hoc selection into other people's pipelines.

2. **No `--version-pr-only` semantic specification**: the flag is invoked at line 1374 but never defined in the body. A reader cannot know what subset of cells `sms_campaign.py --track 2 --version-pr-only` actually runs.

3. **`fail < 0.10` threshold contradicts §6.5.3**: the YAML uses 0.10 as the PR-gate threshold (line 1375 `sms_pr_gate.py … fail < 0.10`), while §6.5.3 line 1387 prescribes 0.20 as the "basically adequate" threshold. These two thresholds are incompatible — a PR can pass §6.5.2's CI gate (≥0.10) and fail §6.5.3's audit threshold (≥0.20). The two stakeholder pathways will produce contradicting verdicts on the same MR. No reconciliation is provided.

**Recommendation**: either delete the YAML fragment entirely (R3 round-1 W5-FIX (c) recommendation), or rewrite it to (a) remove the env-var trap, (b) use a single threshold consistent with §6.5.3, (c) add explicit semantics for `--version-pr-only`, (d) carry a "Resource estimate" sub-paragraph (R3 round-1 W5-FIX (a)).
